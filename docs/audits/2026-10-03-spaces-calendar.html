Spaces & Google Calendar integration

I read the whole spaces and calendar surface and ran a 10-probe Convex test suite against the real functions. Ten defects, eight proven by a failing or instrumented probe. The worst two: deleting a space leaves its activity history behind, and “Resync” cannot put back an event you deleted in Google — it needs two clicks.

Both features ship behind VITE_ENABLE_SPACES / VITE_ENABLE_CALENDAR (default off), so nothing here is reachable in the default build yet. These are the bugs to fix before the flags flip.

Bottom line

Authorization is solid: I could not break the ownership or membership gates. The failures are in lifecycle cleanup and in the calendar’s “event removed on Google’s side” path. One is a deployment hazard that can make every existing personal board look empty.

S-1 deleteSpace orphans every task’s activity history high spaces

Delete a shared space and the projects, tasks and members go — but the activity log rows behind the tasks stay in the database forever. The cascade passes the tasks’ internal Convex _id to the activity lookup, while activity rows are keyed by the app-facing task id. The lookup matches nothing, so nothing is deleted.

This is the one probe I wrote to assert the intended behaviour, and it fails: after deleteSpace, one activity row remains with taskId: 't1' while the task itself is gone. On a busy space this is unbounded table growth and a cascade that quietly does not do what its own comment says.

Fix direction
In deleteSpaceSide, look activity up by the task’s app id, not the Convex _id — exactly as tracker.ts already does. Carry both ids (or the task rows) through the continuation.

C-1 “Resync” cannot restore an event deleted in Google — it takes two runs high calendar

The Resync control promises it will “re-push every synced task, including any event deleted in Google”. It does not. When Google answers a patch with 404/410, the sync clears the local event id and returns a failure (event_removed) whose own message says “Use Resync calendar to put it back”. A single click therefore clears the id and fails; only the next click creates the event.

The probe drives the real action with the network mocked at the fetch boundary: run one sends a PATCH and gets 404, returns event_removed and nulls the id; run two sends a POST and succeeds. Every task whose event was deleted this way — including every task after you toggle sync off and back on — costs two resyncs.

Fix direction
Give the explicit syncTask path a “recreate on missing” mode, or have the resync clear stale ids before pushing. Keep the background scheduler’s current behaviour, which deliberately does not resurrect events the user deleted.

S-2 Un-migrated rows disappear from personal boards high spaces

Personal board reads now filter on spaceId = null through a new index. Rows written before that field existed have no spaceId key, and Convex omits a document from an index when the indexed field is absent. So until the manual backfillSpaceId migration runs, every pre-existing personal project and task is invisible: the board renders empty even though the data is still in the database.

The probe inserts a row exactly as the old code wrote it (no spaceId), queries the board (0 projects), runs the backfill, and queries again (1 project). The schema comment acknowledges the field is optional “until the backfill has run everywhere”, but nothing enforces the order — no deploy hook, no runtime fallback, and the reads do not treat a missing field as personal the way backup import does.

Fix direction
Either run the backfill as part of the deploy, or make the personal read tolerant of absent spaceId (as personalRows in backup already is) until the backfill is verified. migrations.verifySpaceId already exists to gate the switch.

C-2 Turning sync off deletes the Google event but keeps its id medium calendar

Switch calendar sync off and the cleanup deletes the events from Google, but the tasks keep their calendarEventId. That leaves a dangling pointer. The UI still counts those tasks as “synced”, and the next resync patches an event that no longer exists — which is exactly the two-run failure above. The two bugs compound.

Fix direction
When the cleanup deletes an event, also clear calendarEventId on the task (keep addToCalendar, the user’s intent). That makes re-enabling sync a single clean resync.

S-3 Removing a member leaves their tasks assigned to them medium spaces

Remove someone from a space and their membership goes, but any task assigned to them still points at their id. The assignee dropdown only lists current members, so those tasks render with no valid selection — the person is gone from the member list but still the owner of work. The task dialog can still clear it to “Unassigned”, so it is recoverable, but the default state is wrong.

Fix direction
In removeMember, unassign (or reassign to the owner) that member’s tasks in the same transaction, and log an activity row for it.

C-3 A bad Clerk secret is reported as “no Google account connected” medium calendar

The token fetch tries two Clerk provider slugs and treats any non-OK HTTP response as “try the next one”. When the deployment’s CLERK_SECRET_KEY is wrong or expired, Clerk answers 401 for both, and the user is told “No Google account is connected to this Clerk user” — a user-action message for an operator problem. The same swallow hides 403s and 5xxs.

Fix direction
Distinguish 401/403 (server credential problem → not_configured) from 404 (provider not linked → try the next slug / not_connected).

S-4 deleteSpace reads the whole space in one transaction medium spaces

The cascade is advertised as batched so “a space larger than one transaction still goes without tripping the limits”. The writes are batched — but the first thing deleteSpace does is .collect() every member, project and task. That read scales with the space, not with the 200-row batch, so a large enough space cannot be deleted at all: the first transaction dies before any continuation is scheduled. Convex’s default read cap is 32,000 documents / 16 MB; a space above that fails.

The probe lowers the document-read limit to 250 and creates 300 tasks, which makes the failure visible at test scale. At default limits the same shape bites at roughly 32,000 tasks (or 16 MB of task documents). A second, related limit: the continuation passes whole id arrays through the scheduler, and Convex arrays cap at 8,192 values.

Fix direction
Page the initial read the way the import and sync-off cleanup already do (paginate, then schedule), instead of collecting all three tables up front.
Proof · test D

U-1 Client subtree walk recurses forever on a parent cycle medium client

The server’s subtree walks all carry a visited set, with a comment saying a restored backup can carry a cycle. The client’s descendantIds, used by the optimistic move and delete updates, has no such guard. A two-node cycle sends it into infinite recursion and a RangeError, which crashes the optimistic update.

Mutations reject a self-parent, but backup import inserts parentId from the file with no validation, so a hand-edited or round-tripped backup can create the cycle. Cycle nodes are hidden from project cards (they have no root path), but they can still appear in the flat Timeline if they have a due date; opening one and pressing Delete runs descendantIds and throws.

Fix direction
Add the same visited set the server uses. One line, and the two implementations stop disagreeing.
Proof · tsx probe
input: a.parentId=b, b.parentId=a (a 2-cycle)
THREW: RangeError - Maximum call stack size exceeded

U-2 A space task’s dialog shows “Calendar sync is on its way” low calendar UI

Calendar sync is personal-only by design, but the task dialog renders the ComingSoon placeholder for shared-space tasks even when the calendar flag is on. A collaborator on a shared board is told the feature is coming when it exists and is simply not available to them. It should render nothing, or a one-line “personal tasks only”.

Fix direction
Branch on spaceId === null alone for the placeholder; render nothing (or a personal-only note) inside a space.

U-3 Enter key double-submits the create dialogs low spaces UI

The New Space and New Project dialogs submit on Enter without checking whether a request is already in flight. The buttons disable themselves while pending, but Enter bypasses the button. Press Enter twice quickly and you create two spaces or two projects. The same pattern appears in both dialogs.

Fix direction
Guard handleCreate / submit on isPending, matching the disabled button.

Checked and holding

These probes passed. They are the parts of the implementation I tried to break and could not.

  • Join throttleCounts only codes that fail to resolve (re-opening a valid link never burns an attempt), and blocks the 11th attempt within the window. Test B: nine not_found, then throttled.
  • Ownership succession and code rotationWhen the owner leaves, the longest-standing member becomes owner and the invite code rotates; the old link stops working and the new one joins. Test H.
  • Authorization gatesNon-owners cannot delete, reset or remove; non-members cannot read the board or the member list. Test J: every probe rejected.
  • Cascade (activity aside)deleteSpace removes projects, tasks, members and the space document itself. Test I.
  • Token isolationThe Google access token is fetched from Clerk with the deployment secret and used only inside the Convex action. The browser never receives it.

How the probes run
convex-test executes the real Convex functions in-process against an in-memory database. Network is stubbed at fetch, so the calendar probes prove the code’s decision logic, not live Google behaviour. The suite ran in ~1.4 s and peaked at ~220 MB.

Caveats and what I did not test

  • No live Google or Clerk callsThe calendar probes stub the network. They prove which branch the code takes (404 → event_removed, 401 → not_connected), not Google’s real responses.
  • Delete-scale limit is demonstrated at lowered limitsFinding S-4 uses documentsRead: 250 with 300 tasks so the unbounded read is visible at test scale. At Convex defaults the same failure needs ~32,000 tasks or ~16 MB of task documents.
  • The cycle needs a cyclic parentIdMutations reject self-parents, so the client crash needs a cycle to reach the database — the realistic route is a hand-edited or round-tripped backup through importBackup, which does not validate parentId.
  • No browser passI did not run the UI end to end; the two UI findings are code reads. The backend findings are runtime-proven.
